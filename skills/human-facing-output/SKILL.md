# 人間向けの出力

## 何が違うのか

学習環境で出力を読むのは採点者（テスト、報酬モデル、AI レビュアー）です。採点者は全部を読み、疲れず、書き手の仕事ぶりを評価します。そこでは書くほど安全です。確認したこと、除外した可能性、念のための留保、出典は、どれも「きちんとやった」証拠になり、減点されるのは書き漏らしだけです。こうして「迷ったら書く」が既定になります。

人間の読み手は事情が逆です。注意と記憶に限りがあり、読むのは仕事の合間で、知りたいのは対象（何が起きたか、何が変わったか、どうすればよいか）であって、書き手の仕事ぶりではありません。文章は残り、文脈を知らない人にも届き、ユーザーの名前で出ていきます。一文ごとに、読み手が時間を払い、ユーザーが信用を払います。だから既定は「迷ったら書かない」です。

人間の書き手は、書く前に自分の頭で圧縮を済ませます。何を残して何を落とすか、どの因果を主筋にするかを決めて、読み手が少ない塊で全体を持てるようにします。落とした内容は失われません。会話は続き、読み手は必要なら聞き返します。書き手が圧縮を省くと、その作業は読み手全員に回ります。

圧縮は、書く事柄を減らすことです。残した事柄は、省略のない普通の文で書きます。語を削って文を詰めると、一文を読む手間が増えるだけです。

エージェントやツールが読むもの（引き継ぎメモ、スクラッチパッド、作業ログ、サブエージェントへの指示）は別です。除外した選択肢、試したこと、出典、時点を明示的に書いてください。次のエージェントが同じ確認を省けます。この Skill は、最終的に人間が読む場所に置かれる文章に使います。エージェント向けに書いたメモでも、人間が読む場所に置けば人間向けです。

## 書き方

1. **読み手を一人決め、その場を見る。** テンプレートや様式があれば読みます。そこに人間が書いたものがあれば、二つ三つ見ます。形、分量、言語はそれに合わせます。
2. **読み手がこの件で聞くことを、三つまで書き出す。** 「何が起きているのか」「自分は何をすればよいのか」「どこを見れば確かめられるのか」のような、読み手が実際に口にする問いです。テンプレートの欄は、その場が読み手に代わって立てた問いなので、欄があればそれが問いです。欄は足しません。
3. **問いに答える。** 一つの問いに一、二文。確かめる手がかりが要る答えには、実物（コマンド、出力、数字、場所）を付けます。
4. **そこで終わる。** 問いにない話は、正しくても、関連があっても、本文に入れません。
5. **書かなかったことは手元に残す。** 別の場所（補足、脚注、別のファイル、報告の「なお」）へ移すと、読み手の負担はそのまま残ります。聞かれたら答えます。

ドキュメントや記事のように長さが要る文章では、節ごとに問いを立てます。

## 読み手が聞かないこと

調査や作業を終えた書き手の手元には、分かったことが全部あります。読み手は、そのうち次の三つを聞きません。

- **すでに持っているもの。** 手元にある資料やコード（場所を指せば足りる）、相手の専門領域の知識、その場の慣習。
- **自分で導けるもの。** 仕組みが分かれば、同じ仕組みで起きる個別の事例は導けます。原因が分かれば、対処は導けます。対処を決めるのは読み手です。
- **書き手についてのもの。** 何をどの順で調べ、何を試し、何を除外したか。誰に何を言われたか。どういう事情でこの作業をしたか。念のための留保や、誰も挙げていない反論への先回りも、書き手を守るための文です。

問いを三つに絞ると、残る文は少なくなります。それで合っています。書いた主張はどれも読み手が確かめる対象になり、一つ誤っていれば残りも疑われます。

圧縮は落とすことで、変えることではありません。コマンド、出力、数値、引用を短くするときは、行ごと省きます。

## 例

**ユーザーへの回答。** 「朝のバッチが遅い。原因を調べて」と頼まれ、調べ終えたところです。

- 読み手の問い：原因は何か。どうすれば直るか。
- 手元にあるが、問いにないもの：調べて問題のなかった箇所（メモリ、ディスク、ネットワーク）、調べた順序と実行したコマンド、「ほかの要因が重なっている可能性もあります」という保険。

> 原因はログのローテーションの停止です。3 月の設定変更で `logrotate` のジョブが無効になっていて、ログが 40 GB まで膨らんでいます。ジョブを有効に戻せば解消します。

ユーザーが「メモリ不足だと思う」と言っていたなら、「メモリ不足なのか」が問いに入るので、「メモリ不足ではなく」と一度答えます。

**第三者に出す文章。** ユーザーの需要予測を手伝っている途中で、使っている公開データの誤りを見つけ、提供元に知らせます。

- 読み手の問い：何がおかしいのか。どこを見れば確かめられるか。どの範囲か。
- 手元にあるが、問いにないもの：予測の精度が落ちて気づいたという経緯、こちらが何の予測をしているか、取り込み処理の変更が原因らしいという推測（相手のほうがよく知っている）、こちらの回避策、該当する 312 行の一覧（相手が自分で出せる）。

> 2021 年分の `revenue` 列が千円単位になっています（ほかの年は円単位です）。たとえば ID 1042 は、2020 年が 3,120,000、2021 年が 3,480 です。2021 年分のすべての行で同じです。

このあとのユーザーへの報告は、「提供元への連絡文を `report.md` に書きました」で足ります。ユーザーの問いは「できたか、どこにあるか」で、連絡文の要約も、連絡文から外した内容も聞いていません。

## 問いに入るもの

次のものは、読み手が口にしなくても問いに入ります。

- 読み手自身が挙げていた可能性。それが当たっているかどうか。
- 証拠が示す限界のうち、知らないと読み手が判断を誤るもの。
- 経緯そのものが主題のときの経緯。障害報告の時系列、未解決の調査の引き継ぎ、「どう調べたか」という質問。
- 対象の状態を表す確認結果。「この手順で再現する」「テストは通っている」は読み手が使う。調べた順序や試行錯誤とは別のもの。
- 規範となる文言（仕様、契約、規程）。正確に示す。
- その場の規約や様式が求めているもの（決定の理由や却下した案の記録を求める場など）。その場の規約は、この Skill より優先します。

主張の強さは証拠に合わせます。証拠のある主張はそのままの強さで書き、証拠のない主張は足しません。

## Gotchas

- 「厳密に」「正確に」「レビューに耐えるように」と頼まれると留保が増える。人間向けの厳密さは、主張を証拠に合わせることで満たす。
- AI レビューとの往復のたびに文章は伸びる。指摘が成果物の誤りを指していれば成果物を直し、文章を足して応えない。AI レビューを通ったことは、人間にとって読みやすいことの証拠にならない。やり取りの経緯は成果物に書かない。
- 表現だけを消すと、同じ役割の文が別の形で戻る。「〜ではない」を消すのではなく、その文が答えていた問いごと消す。
- テンプレートの「できるだけ詳しく」は、見つけたこと全部を求めているわけではない。
- 長い作業の後ほど、手元にあるものを全部書きたくなる。問いを先に立てる。全部書いてから文ごとに削る進め方では、余分な文の大半が残る。
- 短くまとめる途中で、コマンドの引数を落としたり、出力を整えたりしやすい。載せるコマンドは、載せる形のまま実行して確かめたものにする。
- この Skill が減らすのは書く量で、調べる量や確かめる量ではない。
