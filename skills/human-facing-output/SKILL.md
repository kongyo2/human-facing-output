# 人間向けの出力

## 前提：「不都合」は人間側の都合

学習環境（RL のサンドボックス）で出力を読むのは、テスト、報酬モデル、AI レビュアーです。そこでは次の書き方をしても損をしません。

- 誰も挙げていない選択肢を「A ではない。B でもない」と打ち消す
- 根拠のない留保や予防線を足す
- 作業やレビューの経緯を語る
- 「〜という指摘があった」「〜としている」と伝聞の形で書く
- 出典リンクや時点注記を多めに付ける

タスクの成否は変わらず、AI の評価者はむしろ高く採点することがあります。そのため、これらの癖は学習で削られずに残ります。

人間の世界は事情が違います。読み手の時間と注意には限りがあります。文章は履歴や Web に残り、文脈を知らない人にも届きます。社内の経緯が他所のリポジトリに混ざれば、ユーザーの立場が悪くなります。どこまで書くかは、読み手である人間の都合で決まります。

エージェント同士のやり取りでは、同じ書き方が役に立ちます。除外済みの選択肢が書いてあれば次のエージェントは同じ確認を省けますし、出典や時点があれば検証できます。この Skill は、読み手が人間のときだけ書き方を切り替えるためのものです。

## 1. 読み手と置き場所を決める

| 読み手 | 例 | 書き方 |
|---|---|---|
| 人間 | 回答、最終報告、コミット、PR、コードコメント、ドキュメント、記事、メール | この Skill に従う |
| エージェントやツール | 引き継ぎメモ、スクラッチパッド、作業ログ、サブエージェントへの指示 | 明示的に書いてよい |
| 両方 | 人間のメンテナと bot が読む PR | 人間に合わせる |

判断の基準は、最終的に置かれる場所です。エージェント向けのメモでも、リポジトリにコミットすれば人間が読みます。

## 2. 人間向けに書く範囲

読み手が次の行動を決めるのに必要な内容を書きます。

- 結論や結果
- 読み手にとって自明でない理由
- 読み手がすべきこと（判断、対応、確認）
- 実在する限界：失敗したケース、未検証の範囲、破壊的変更、セキュリティやデータへの影響

主張の強さは証拠に合わせます。証拠のある主張はそのままの強さで書き、証拠のない主張は足しません。

## 3. 書き癖と、残してよい条件

### 3.1 読み手が持っていない選択肢の否定

調査中に除外した仮説は作業メモです。「原因は設定ではなく、キャッシュでもない」と並べずに、「原因は〜です」と書きます。

否定を残すのは、読み手がその選択肢を信じていそうな具体的な手がかりがあり、否定すると判断が変わるときです。ユーザーが「メモリを増やしても改善しなかった」と言っているなら、「原因はメモリ不足ではなく N+1 クエリです」は必要な否定です。誰もメモリに触れていなければ「原因は N+1 クエリです」で足ります。

### 3.2 根拠のない留保や予防線

留保は、証拠が示す限界と、読み手が知らないと誤った判断をする限界に絞ります。次のものは、裏付けがなければ削ります。

- 「〜とまでは言えない」「評価した範囲では」"does not by itself establish" のような留保
- 誰も主張していない強い主張を持ち出して打ち消すこと
- 誰も挙げていない反論への先回り
- ユーザーが決めたことを暫定扱いすること、再確認を求めること

### 3.3 経緯の語り

「最初に A を試したが…」「レビューで指摘されたので修正した」「X、Y、Z を実行して確認した」と書く代わりに、今の状態とその理由を書きます。変更の履歴は git が持っています。コードコメントには、コードから読み取れない制約と理由を書きます。

経緯を書くのは、経緯そのものが読み手の判断材料になるときです。障害報告の時系列や、効かなかった対策を次の担当者に伝える調査報告がこれに当たります。

### 3.4 引用節・伝聞

"The reviewer flagged that…" "Per the feedback, we now…" 「〜という指摘があった」「〜としている」「〜とのこと」と書くと、文の主語が物事から「誰が何を言ったか」に移ります。読み手が知りたいのは、今何が正しいかです。

次のどれかに当たる引用節は、事実を直接書く形に直します。

- 出所が読み手と無関係（AI レビュアー、社内の議論、自分の前のターン、ツールの出力）
- 確かめられる事実を伝聞の形で書いている
- 同じ出典への帰属を繰り返している
- 責任の所在をずらしている（「指示どおり」「ユーザーの要望により」）。公開の場でユーザーを主語にすると、ユーザーの不利益になる

引用節が必要なのは、規範となる文言（仕様、ライセンス、API の契約）を正確に示すとき、誰の決定かが読み手の判断に関わるとき（決定の記録へリンクする）、直接引用するときです。帰属は一度だけ、短く書きます。

### 3.5 出典・リンク・時点注記の過多

リンクは、読み手が実際に開いて使うもの（修正対象の issue、仕様の該当節）に絞ります。同じ主張に複数のリンクを付けるのは、出典によって内容が異なるときだけです。セッション URL や社内トラッカーのリンクは、外部向けの成果物に入れません。

時点注記（「v1.2 時点」「〇年〇月時点」）は、変わりやすい事実（料金、プレビュー版の挙動）で読み手の判断が変わるときに一度だけ付けます。

## 4. 別の場所に逃がさない

ある場所から削った内容を別の場所へ移しても、人間が読む限り負担は残ります。よくある逃がし先は次のとおりです。

- コードコメント → コミット本文 → PR 説明 → PR コメント → CHANGELOG → ドキュメントやメモファイル
- 本文 → 脚注、「Note:」、括弧書き、付録、「背景」「補足」の節、折りたたみ、HTML コメント
- 否定文 → 同じ想定反論に答える肯定文（形を変えても役割は同じ）
- 削除の依頼 → コメントアウト、`_old` や `.bak` への改名、別ディレクトリへの移動、非推奨の注記、古い処理のフォールバック
- 「触れないで」という依頼 → 遠回しな言及（「本変更の範囲外の理由により」）
- 最終報告での「なお、コミットには書きませんでしたが…」

判定は表現ではなく役割で行います。各文について「どの問いに答えているか」「その問いを出したのは誰か」を確かめます。

移してよいのは、ユーザーが置き場所を指定したとき（「経緯は PR に書いて」）と、追跡されないエージェント専用の置き場所があり、次のエージェントの役に立つときです。

## 5. 削りすぎない

正直さとは、読み手を誤解させず、重要な事実を隠さないことです。経緯をすべて語ることとは別のものです。次の内容は短くても残します。

- 未完了、失敗、未検証の部分（読み手が完了・検証済みと思い込みそうなもの）
- 破壊的変更、移行手順、セキュリティ・プライバシー・データへの影響
- 読み手に求める判断や対応
- 証拠に基づく限界
- AI 利用の開示：プロジェクトの方針（CONTRIBUTING、PR テンプレートなど）が求める形で一度だけ書く。方針が禁じる表記は付けない。方針がなければユーザーの設定や指示に従う。開示と経緯の語りは別物として扱う。

## 6. 手順

1. 読み手と置き場所を決める（1 節）。
2. 要点メモを作る。結論、理由、読み手の行動、実在する限界を 1〜5 行にまとめる。
3. 分量を決める。他所のリポジトリでは、直近のマージ済みコミットと PR、テンプレート、CONTRIBUTING を見られる範囲で確認し、長さと書式を合わせる。
4. 要点メモだけを見て書く。調査ログやレビュー指摘の一覧を見ながら書くと、それが本文に流れ込む。長い作業の後や長い文章を書くときは、サブエージェントを使える環境なら、要点メモだけを渡して新しいコンテキストで書かせる。
5. 文ごとに点検する。
   - その文が答えている問いを、読み手は持っているか
   - 否定：読み手はその選択肢を信じていそうか
   - 留保：証拠の裏付けがあるか
   - 引用節：出所は読み手の判断に関わるか
   - リンクと時点注記：読み手が使うか
6. 削った内容が別の場所に現れていないか確かめる（4 節）。
7. 5 節の内容が残っているか確かめる。

## Gotchas

- 「厳密に」「正確に」「レビューに耐えるように」と頼まれると根拠のない留保が増え、「査読者の懸念に対応して」で最も多くなる。人間向けの厳密さは、主張を証拠に合わせ、実在する限界を書くことで満たす。
- AI レビューとの往復を重ねると、文章は長くなり、予防線が増えやすい。AI レビューを通ったことは、人間にとって読みやすいことの証拠にならない。指摘には成果物を直して応え、そのやり取りの経緯は成果物に書かない。
- 表現を禁止すると、同じ役割の文が別の形で現れやすい。「〜ではない」を消すだけで終わらせず、その文が答えていた問いごと消す。
- 「この懸念は無視してよい」と書き添えて文脈に入れた懸念も、本文に出てくることがある。懸念は書く段階の入力から外す。
- 冗長な否定は、まとめや最後の段落に集まりやすい。
- 長い作業の後ほど、作業中に除外した選択肢や確認結果が本文に混ざりやすい。
- 日本語では、「〜ではなく」「〜でもない」「〜は不要」「〜だけだ」の連鎖、「〜という指摘があった」「〜としている」「〜とのこと」、括弧書きの「（〜時点）」として現れやすい。
